# Security and performance boundaries

## Heuristic structural review

`analyze` inspects validated rules without executing matches. It reports candidates involving nested/adjacent variable repetition and overlapping choices, plus informational wildcard, line-anchor and generated-size notes. Findings carry compiler locations/spans and review guidance. The local workshop presents them on demand as source-linked buttons; edits invalidate cached results and invalid input clears old notes.

These are review prompts, not proven ReDoS vulnerabilities, measured backtracking or certification of safety. The witness model recognizes selected literal/range/positive-class overlaps and ASCII case pairs; Unicode property aliases, complex bodies, negation/subtraction, backreferences, lookaround execution and search restart costs are not fully modeled. Unknown witnesses are not treated as disjoint sets. Both false positives and missed expensive patterns are possible. **No findings does not prove performance safety.**

Nested repetition and overlapping alternatives are documented review patterns in [CWE-1333](https://cwe.mitre.org/data/definitions/1333.html) and [OWASP's ReDoS description](https://community.owasp.org/attacks/Regular_expression_Denial_of_Service_-_ReDoS). Their runtime effect depends on the engine, pattern, search context and input; the analyzer does not infer that effect. It preserves existing compiler budgets/capability errors and performs no matching on the UI thread. Example matching still uses a terminable isolated worker with an enforceable deadline. Copied patterns need deployment-engine controls regardless of findings. See [the API contract and limits](LANGUAGE.md#structural-risk-review).

## Inputs and compilation

The version 1 parser accepts only the phrases in [LANGUAGE.md](LANGUAGE.md). It rejects unknown lines instead of returning a partial regex. Literal text and character-list items are escaped for their distinct regex contexts, and the compiler validates emitted source with JavaScript `RegExp` before returning it. Input rules are limited to 16,384 UTF-16 code units and 200 lines; numeric repetitions are limited to 1,000.

The workshop keeps oversized rule text for repair. Its counter shows “Over limit” without splitting that value; error navigation splits no more than 16,385 UTF-16 code units to include the first excess unit. The complete input stays in the field: these bounds apply to the application's splitting work.

Reverse translation reads a documented subset of native Unicode regex syntax without matching the supplied pattern. The CLI's `--reverse` reader rejects malformed UTF-8 and bounds streamed input to 16,392 UTF-16 code units, including outer whitespace, delimiters and flags. The shared literal reader applies the same whole-input budget in both the workshop and CLI before trimming, then checks delimiters, raw line breaks and flags before native syntax validation; the reverse API independently limits regex source to 16,384 code units and checks emitted rules against the existing parser. Unsupported syntax fails instead of becoming raw regex in the rule language.

The reverse API reads stored metadata through native getters, bypassing overridden instance properties and matching methods. It rejects unsupported flags, missing Unicode mode and oversized source before parsing, without cloning or reconstructing the supplied regex. Reading native source and constructing a regex before calling this API still depend on the JavaScript engine; this is not a bound on arbitrary caller allocations.

Explicit compiler flags are bounded to eight unique native letters before further validation. u/v conflicts and unavailable runtime features fail explicitly; native v class punctuation is escaped in its own context. g/y retain native cursor state for API consumers. The workshop resets every example to zero, including its full-match fallback, combines internal g/d without duplicates and preserves sticky gaps. Its worker accepts only canonical flags with exactly one Unicode mode; matching still runs behind the same enforceable termination deadline.

Unicode direction controls appear as visible escapes in generated source and human-readable results, reducing misleading [visual ordering](https://blog.unicode.org/2022/03/avoiding-source-code-spoofing.html). This presentation does not remove them from matching data: source-text metadata and editable examples retain their original contents, and CLI JSON preserves the data round trip.

The shared display policy also escapes C0/C1 control characters, DEL and Unicode line separators in generated source and human-readable values. Copied patterns, explanations, diagnostics, trace text and match feedback contain visible escapes while editable input and original source metadata retain the data. The CLI applies the same policy to arguments and native file errors separately from its own formatting line breaks; JSON decoding restores the original values.

Both bounds of `between n and m <item>` obey the numeric ceiling, with `0 ≤ n ≤ m`. Adjacent repeated atoms can still cause expensive backtracking, including when each repetition has a finite upper bound. Browser tests cover this with a compiler-generated bounded expression as well as an intentionally pathological raw expression; neither result guarantees that a copied regex is safe on arbitrary input.

The browser allows compiled regex sources up to 131,072 UTF-16 code units. This covers the largest escaping expansion from the 16,384-code-unit rule limit: a literal U+2028 or U+2029 becomes an eight-code-unit Unicode escape. Matching accepts examples up to 2,048 UTF-16 code units, with no more than 100 examples per run. The editor keeps oversized values intact for repair and marks them invalid; testing stops until they are shortened or removed, without sending those values to the worker or testing a truncated prefix. The worker independently rejects larger or malformed requests. These limits are product constraints, not a guarantee that every generated expression is fast in every other runtime or on every input size. Users should test the expression in the runtime where they intend to use it.

## Browser execution

The dev.8 workshop additionally bounds each complete result batch to 1,000 match records, 20,000 capture records and 1,048,576 UTF-16 text units. Text includes match/capture values, escaped details and native replacement output; an error reply has the same text ceiling. The private shared budget is reserved before match/capture records are allocated in the worker and checked again by the controller before resolving results for rendering. Overflow discards the whole result batch and reports `Example output is too large. Use fewer examples, captures or matches.`; it never silently omits examples or marks partial results as passing. The existing per-example enumeration limit and exact-expectation boundary probe are preserved. A later check starts fresh after controller errors.

These are bounds on the known result records and text, not exact serialized-byte or engine-allocation limits. The native worker checks before transferring its reply. Controller validation occurs after receipt and cannot prevent structured cloning of an externally forged message. The 1,200 ms termination deadline remains necessary for expensive native matching; copied regexes do not gain these worker limits.

The homepage demo accepts matching input up to 80 UTF-16 code units. It keeps longer values intact, marks them invalid and skips regex execution, with a visible link to the workshop's larger testing limit. It only exposes the fixed demo recipes, not custom rules.

The static workshop compiles rules locally. It loads its code and public recipe fixtures from the same origin; it does not submit typed rules or examples to an application backend, add telemetry or require an account. The hosting provider can still see ordinary requests for the static files and may keep access logs.

Matching examples runs in a dedicated Web Worker, not on the UI thread. An edit cancels a pending check and terminates its worker; a completed worker can serve the next check. Each request creates fresh regexes and example results. The controller terminates a worker and reports an error if it has not responded within 1,200 ms. Errors and explicit cancellation also discard an idle worker, so a later check starts fresh. The worker accepts canonical `d?g?i?m?s?(u|v)y?` flag sequences and examples with unique safe-integer IDs, bounded string values and boolean expectations. It validates the complete batch before constructing or running a regex, including sparse entries and malformed later examples; an expensive earlier example cannot replace their stable validation error with a timeout. This limit protects the workshop interaction; it does not change the behavior of a regex copied into another program. Browser tests run pathological and compiler-generated bounded expressions in already loaded workers, confirm timeout and then confirm that the same controller can run a normal expression again.

The UI writes rules, examples, diagnostics and explanations through `textContent` or form values. It does not use user text as HTML or JavaScript. The document has a restrictive Content Security Policy. The browser tests include an HTML-looking literal, oversized input, same-origin resource checks and zero console errors in the reference scenarios.

Structural diagrams use the same validated AST and compiler budgets without running matches. The SVG renderer escapes XML text, visibly escapes controls, lone surrogates and XML-invalid BMP noncharacters, and emits metadata only from validated rule locations and generated spans. It emits no scripts, event attributes, links, foreign objects or external resources. Presentation attributes keep the standalone drawing compatible with the workshop's existing Content Security Policy. The workshop imports only this generated SVG, checks its namespace and XML parse result, and discards stale diagrams after edits or errors. The diagram describes structure; it neither records engine execution nor proves performance safety.

The controller validates current worker replies before resolving a test: a safe-integer request ID, either a string error or at most 100 result objects, unique safe-integer result IDs, boolean match/pass fields and string details. Malformed replies report `Invalid example test reply.` and discard the worker immediately, allowing the next check to start fresh. Valid older request IDs and messages from idle or retired workers are ignored. This checks the reply structure; it does not independently re-run matching on the UI thread.

## Verification and limits

Precise expectations are validated and snapshotted before any matching. The controller recomputes span/capture/replacement comparisons from bounded native results and rejects forged check fields. A native probe beyond 100 search records prevents a truncated list from passing exact assertions. Replacement streams native matches inside the same worker deadline, with 128-unit templates, 100 native global matches and a 65,536-unit output ceiling. No callback is evaluated and oversized output is rejected atomically.

Versioned fixture files are limited to 4 MiB before reading and fully validated before applying; malformed data and stale asynchronous reads retain the current workspace. Per-case expectation JSON is bounded to 8,192 UTF-16 units. Imported strings retain exact line endings until their native example field is edited. Manual local save/restore catches denied storage, quotas and corrupt data; invalid drafts cannot replace a saved valid fixture. Browser storage is optional and removable, so durable regression preservation uses explicit JSON export. See [the full fixture contract](TEST_FIXTURES.md).

Capture exploration runs in the same isolated worker and deadline. Each example displays at most 100 nonoverlapping matches; reaching that limit is reported without claiming there are additional matches. Empty matches advance by Unicode code point, so an empty pattern cannot stall enumeration. Capture counts are bounded to 100 and validated before constructing any regex. Internal `d`/`g` flags do not alter copied source or compiler flags. Capture spans come only from native indices, never substring inference; absent values and participating empty strings are distinct. The controller checks nested counts, range bounds, values against the original input, search order, participation and limit consistency before rendering. Capture tables are built on demand with text nodes, not user-supplied HTML. Without index support the UI explicitly reports unavailable capture positions. These bounds do not prove that copied regexes are safe in another application.

Linked source files are copied as public static-build inputs. Asset versioning edits independent output copies and leaves the original targets unchanged.

The local development server binds to `127.0.0.1`. It resolves the selected static folder and requested files before reading them; URL paths or symlink targets outside that folder return `403`. A symlink selecting the root and links within it remain usable. This development helper assumes trusted local files that do not change during a request.

Run `npm test`, `npm run build` and `npm run test:browser`. Automated accessibility and security tests cover the documented cases, while broader browser/security review and real-user tests remain separate release gates in [ROADMAP.md](https://github.com/OthmaneBlial/Regex-For-Humans/blob/main/ROADMAP.md). The development preview supports bounded nested groups, references, ordered alternatives and native lookarounds. Alternation can increase backtracking cost, especially with nested repetition; input limits and the terminable matching worker remain necessary. The trace describes structure and does not prove performance safety. Arbitrary regex injection and other engines remain outside the current language; adding them requires a new complexity and compatibility review.
